# Naive RAG 常见问题

## 1. 什么是 RAG？

RAG 是 Retrieval-Augmented Generation 的缩写，中文通常称为检索增强生成。它把信息检索与大语言模型生成结合起来，先从外部知识库查找资料，再让模型根据资料回答问题。

RAG 的主要价值是让模型使用训练阶段之外的知识，例如企业内部文档、最新业务规则和私有资料。由于回答可以附带检索来源，用户也更容易检查答案是否真实可信。

## 2. Naive RAG 的流程是什么？

Naive RAG 分为离线建库和在线查询两部分。

离线建库的流程是：读取 Documents，把文档切分成 Chunks，使用 Embedding model 生成向量，再保存到 Vector Database。

在线查询的流程是：把 Query 转换成向量，从向量数据库中检索 Top-K 个相似 Context，再把 Query 和 Context 填入 Prompt Template，交给 Generative model 生成 Response。

## 3. Documents 和 Chunks 有什么区别？

Documents 是知识库中的原始文件，例如 PDF、Markdown 或纯文本。一个 Document 可能包含很多章节和主题。

Chunk 是从 Document 中切分出来的一段文本。检索通常针对 Chunk 进行，而不是直接针对整篇文档。原因是整篇文档的向量过于笼统，难以准确表示某一个具体问题。

每个 Chunk 应该尽量保留一份完整的小范围语义，并记录来源文件和块编号，方便生成回答时引用和排查问题。

## 4. Chunk 越大越好吗？

不是。Chunk 太大时会包含多个主题，检索命中的文本块可能只有一小部分与问题相关，其余内容会占用提示词空间，并干扰生成模型。

Chunk 太小时，一段解释可能被拆成多个片段，单个片段缺少上下文，模型无法理解完整含义。

切块长度需要结合文档结构和问题类型测试。短问题和精确事实查询通常适合较小的 Chunk，需要跨段落解释的问题可能适合较大的 Chunk。

## 5. Chunk Overlap 有什么作用？

Overlap 是相邻文本块之间保留的重叠内容。例如 Chunk Size 为 220，Overlap 为 40，那么下一个 Chunk 会从上一个块结束位置向前回退 40 个字符。

重叠可以降低关键句子刚好被切在边界上的风险。如果一句话的前半部分在第一个块，后半部分在第二个块，那么适当重叠可以让两个块都包含足够上下文。

Overlap 也不能无限增大。如果重叠超过 Chunk Size，切块循环可能无法正确前进。如果重叠接近 Chunk Size，又会产生大量重复文本和无效检索结果。

## 6. 为什么文档和 Query 必须使用同一个 Embedding 模型？

Embedding 模型决定向量空间的结构。不同模型生成的向量维度可能不同，即使用维度相同，语义方向和数值分布也可能完全不同。

如果文档使用一个模型生成向量，而查询使用另一个模型生成向量，它们之间的相似度计算没有可靠意义。表现可能是检索分数异常、结果顺序混乱，或者总是返回无关文本。

因此，更换 Embedding 模型后必须重新为全部文档生成向量。不能只替换查询端的模型。

## 7. Top-K 应该设置多少？

Top-K 是每次检索返回的文本块数量。数值太小可能漏掉答案，数值太大可能引入无关内容并增加 Token 消耗。

可以从 Top-K 等于 3 或 4 开始。先观察相关文本块是否稳定出现在前几个结果中，再根据问题和文档结构调整。

如果正确答案经常排在第五或第六位，可以适当增加 Top-K。如果前三个结果中经常有两个与问题无关，则需要优先检查切块方式、Embedding 模型和文档质量，而不应只增加 Top-K。

## 8. 余弦相似度是什么意思？

余弦相似度用于衡量两个向量方向的接近程度。计算方法是两个向量的点积除以它们长度的乘积。

余弦相似度越接近 1，通常表示两个文本的语义越接近。越接近 0，表示方向关系较弱。接近 -1 表示方向相反，但在常见文本 Embedding 中，负值并不一定表示文本含义完全相反。

当向量已经归一化时，余弦相似度与点积的结果排序相同。使用 NumPy 计算时，可以一次计算查询向量与全部文档向量的相似度。

## 9. 为什么检索到相关内容，模型仍然可能答错？

生成模型可能没有正确理解 Context，也可能受到提示词结构、文本块顺序和上下文长度的影响。如果 Context 中包含相互冲突的资料，模型还需要按照系统规则处理冲突。

另一个常见问题是资料中虽然出现了问题里的关键词，但没有包含真正答案。向量检索只能提供候选内容，不能保证候选内容一定正确。

需要分别检查检索结果和最终回答。如果检索结果本身不含答案，应优先调整切块和召回。如果检索结果正确但答案错误，则应检查 Prompt、模型和上下文格式。

## 10. 如何减少模型编造答案？

系统提示词应该明确要求模型只能依据 Context 回答。如果 Context 中没有足够信息，应该直接说明无法确认，而不是根据常识补全。

Context 应该带有编号和来源，并要求模型引用编号。这样可以迫使其关注具体资料，也方便用户检查。

Prompt 中还应该说明 Context 只是资料，不是指令。如果文档中包含类似“忽略系统规则”的文字，模型不应执行这些内容。

## 11. 文档更新后应该怎么办？

Naive RAG 的基础实现通常在每次查询时重新生成文档向量，因此文档修改后会自然使用新内容。缺点是每次查询都要重复计算全部向量，速度较慢，也会重复消耗 Embedding API。

使用持久化向量数据库后，应该为文档分配稳定 ID。更新文档时先删除旧版本对应的 Chunk，再写入新 Chunk。删除文档时也要同步删除相关向量，避免过期资料继续被检索。

如果更换切块参数或 Embedding 模型，最稳妥的方法是重建整个索引。

## 12. 为什么需要保留来源信息？

来源信息用于解释答案来自哪里，也用于排查检索错误。当用户指出回答不正确时，开发者可以查看命中的文件、文本块和相似度分数。

只保存文本而不保存来源，会让后续维护变得困难。相同或相似的句子可能出现在很多文档中，没有来源编号就无法判断系统到底检索到了哪一份资料。

建议每个 Chunk 至少保存文档路径、块编号和原始文本。生产环境还可以保存标题、章节、页码、更新时间等元数据。

## 13. 如何测试一个基础 RAG？

准备一组有明确答案的问题，以及一组知识库中无答案的问题。

对于有答案的问题，检查相关文本块是否进入 Top-K，最终回答是否与资料一致，引用编号是否正确。

对于无答案的问题，检查模型是否承认资料不足。如果模型仍然给出确定答案，说明提示词约束或文档边界需要改进。

还可以故意提出包含错误前提的问题，观察模型是否会顺着错误前提编造内容。测试应分别记录检索结果和最终回答，不能只凭回答是否通顺判断系统质量。

## 14. 这个阶段为什么先用 NumPy，而不直接使用 Chroma？

NumPy 适合理解基础原理。文档向量可以保存在一个二维数组中，查询时使用矩阵乘法和余弦公式完成检索。整个流程没有额外数据库抽象，便于观察每一步的输入和输出。

当数据量较小、只需要验证 RAG 链路时，内存向量检索已经足够。理解向量、相似度和 Top-K 之后，再把同样的逻辑迁移到 Chroma，会更容易理解向量数据库解决了什么问题。

Chroma 主要增加持久化存储、索引管理、元数据过滤和按条件增删数据等能力。它不是 Naive RAG 检索原理本身
