Naive RAG 完整示例资料

一、Naive RAG 的基本概念

Naive RAG 是 Retrieval-Augmented Generation 的最基础实现，中文通常称为“朴素检索增强生成”。它的核心思想不是让生成模型记住全部文档，而是在用户提出问题时，先从外部知识库中检索与问题相关的内容，再把这些内容作为上下文交给生成模型。

一个 RAG 系统通常同时包含检索系统和生成系统。检索系统负责从大量文档中找到与问题最相关的资料，生成系统负责阅读这些资料并组织自然语言回答。两套系统通过 Context 连接起来，因此 RAG 可以回答模型训练数据中没有覆盖、但知识库中存在的信息。

Naive RAG 之所以称为“朴素”，是因为它采用最直接的流程：用户问题直接用于检索，检索结果直接放进提示词，生成模型直接输出答案。整个流程没有查询改写、多路召回、结果重排序、答案校验或自动重试。它的结构简单、容易理解，也是学习其他高级 RAG 架构的基础。

二、离线建库流程

离线建库是 RAG 的准备阶段，通常在用户提问之前完成。第一步是收集原始文档，例如产品手册、常见问题、内部规范、技术文档和业务资料。原始文档可以是纯文本、Markdown、PDF、Word 或网页内容。

第二步是读取和整理文档。系统需要提取可读文本，清理重复空白和无效字符，同时尽可能保留标题、段落和来源信息。来源信息很重要，因为最终回答可能需要告诉用户答案来自哪个文件、哪个章节或哪个文本块。

第三步是文本切块。长文档通常不能整体转换成一个向量，因为整篇文档包含过多主题，向量难以准确表示某一个具体问题。系统会把文档切分成多个较小的 Chunks，每个 Chunk 是一段相对独立的文本。常见切块方式包括固定字符数、固定 Token 数、按句子切分和按段落切分。

第四步是调用 Embedding model。Embedding 模型会把每个 Chunk 转换成一个高维向量。向量中的数值不是给人直接阅读的，而是用来表示文本的语义特征。语义越接近的文本，它们的向量通常也越接近。

第五步是把文本块、向量和元数据保存到向量数据库。元数据可以包含文件名、章节标题、块编号和创建时间。向量数据库负责保存这些数据，并支持根据查询向量快速查找相似内容。完成这一步后，离线索引就可以被在线查询流程使用。

三、在线查询流程

在线查询从用户 Query 开始。系统首先读取用户问题，然后把 Query 交给与建库阶段相同的 Embedding 模型，得到查询向量。这里必须保证离线文档和在线查询使用同一个 Embedding 模型，否则两种向量不属于同一个向量空间，相似度结果没有可靠意义。

接下来，系统把查询向量发送给向量数据库。向量数据库使用余弦相似度、点积或欧氏距离计算查询向量与已有文档向量之间的接近程度，并返回相似度最高的一批文本块。

系统通常不会只取一个结果，而是取 Top-K 个结果。Top-K 表示返回相似度最高的 K 个文本块。K 太小可能遗漏真正包含答案的资料，K 太大则可能引入无关内容，还会增加提示词长度和模型调用成本。

检索结果并不等于最终答案。它只是从文档中选出的候选证据。系统需要把候选文本块按照编号和来源整理成 Context，确认上下文长度没有超过模型输入限制，再进入生成阶段。

四、Prompt Template 与答案生成

Prompt Template 是连接检索和生成的提示词模板。一个典型的提示词会包含系统规则、Context 和 Question 三部分。

系统规则通常要求生成模型只根据 Context 回答，不要使用未经验证的外部知识。如果 Context 没有答案，模型应该明确说明资料不足。系统规则还可以要求模型使用编号标注引用来源，方便用户核查回答依据。

Context 部分由检索结果组成。为了让模型区分不同资料，每个文本块应该带有编号和来源。例如第一个文本块标记为资料 1，第二个文本块标记为资料 2。来源信息可以包含文件名和块编号。

Question 部分保存用户的原始问题。模板把系统规则、Context 和 Question 一起发送给生成模型。生成模型阅读上下文后输出 Response。

需要强调的是，Prompt 不能只写“请回答以下问题”。如果缺少约束，模型可能忽略检索内容，直接使用参数知识回答，甚至生成知识库中不存在的信息。明确要求“只依据 Context”是 Naive RAG 降低幻觉的基本手段。

五、一个完整的查询示例

假设知识库中包含产品退款政策。用户提问：“购买后第十天还能退款吗？”

在线系统先把这个问题转换成查询向量，再从向量数据库中检索与退款期限有关的文本块。检索结果可能包含“普通商品支持七天无理由退款”和“质量问题可在十五天内申请售后”。

系统把这些文本块填入 Prompt，生成模型根据资料得出结论：普通商品已经超过七天期限，但如果属于质量问题，还需要进一步确认售后条件。回答中应引用对应的资料编号，而不是只给一个无法核验的结论。

如果文档中完全没有退款期限，模型应当说明当前资料不足。一个可靠的 RAG 系统不仅要会回答，也要能够拒绝在没有依据时编造答案。

六、影响效果的主要参数

CHUNK_SIZE 决定每个文本块的长度。较大的块可以保留更多上下文，但可能混入多个主题，也会增加检索成本。较小的块更聚焦，但可能把一个完整解释拆开，导致信息不完整。

CHUNK_OVERLAP 决定相邻文本块之间重复多少个字符或 Token。适当重叠可以降低关键句子刚好被切断的风险，但重叠过大也会产生大量重复内容，浪费存储空间和模型上下文。

TOP_K 决定最终交给生成模型多少条检索结果。对于事实型问题，Top-K 通常从三个到五个开始测试。对于需要综合多个章节的问题，可以适当增加，并观察上下文是否超过模型限制。

Embedding 模型决定向量质量。不同模型支持的领域、语言和向量维度不同。只要更换 Embedding 模型，就应该重新建立全部向量索引。

七、Naive RAG 的局限

Naive RAG 是单向直线流程。用户问题不会先被改写，检索结果不会进行二次排序，生成答案也不会自动检查。因此，当用户表达模糊、文档切块不合理或检索结果偏差较大时，最终回答质量会明显下降。

固定长度切块可能从句子中间截断，导致一个 Chunk 开头或结尾缺少主语。简单向量检索也可能把字面相似但语义无关的段落排在前面。为此，后续还可以引入按段落切分、混合检索、重排序、查询改写和答案校验。

不过在搭建第一个 RAG 时，不应一开始加入过多组件。应该先用 Naive RAG 跑通完整流程，观察加载、切块、向量化、检索和生成每个阶段的实际结果，再根据问题定位改进点。

八、测试与验收

测试 RAG 时，不应只观察最终回答是否流畅。更可靠的方法是分别检查每个阶段。先检查文档是否被正确读取，再检查 Chunk 数量和内容是否合理。随后检查 Embedding 返回的向量数量和维度是否符合预期。

检索阶段需要准备若干问题，查看最高分文本块是否真的包含答案。如果检索结果错误，即使生成模型回答流畅，整个 RAG 也没有达到目标。

生成阶段需要测试三类问题：知识库能够回答的问题、知识库无法回答的问题，以及问题中包含错误前提的情况。系统应该在有资料时给出有依据的回答，在无资料时明确说明不足，而不能为了显得聪明而编造内容。

完成最基础版本后，可以记录每次查询命中的文本块、相似度分数和最终回答，作为后续调整切块、Top-K 和提示词的依据。
